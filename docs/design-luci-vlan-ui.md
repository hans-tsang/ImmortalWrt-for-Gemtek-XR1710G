# LuCI VLAN UI Design Specification and Configuration Consistency Fix

> **Current status (important)**: `package/luci-app-mesh-conf` has been rewritten. It now only does two things --
> native 802.11s wireless mesh, and discovery of same-model devices on the LAN in wired scenarios to synchronize
> `/etc/config/wireless` (including 802.11k/v/r). **The VLAN editor has been removed entirely**, and the page no longer reads or writes
> `bridge-vlan`.
>
> Therefore, the parts of this document about "two pages editing the same bridge-vlan model" now remain effective only on the
> `switch-vlan` side; `meshconf.js` still uses the design tokens from this document (so
> `tokencheck.js` still applies), but the cross-page port reading issue in §1.1, the port marker consistency in §4,
> and `vlan_port_role()` checked by `portcheck.js` were all retired together with the feature -- `portcheck.js`
> now outputs `SKIP`, rather than failing, when it cannot find that function. Keep this document as the
> single source of truth for tokens and design decisions.

Scope (historical): `/cgi-bin/luci/admin/network/switch-vlan` (the upstream LuCI switch view) and
`package/luci-app-mesh-conf` (this repository's Mesh configuration page). The two pages used to edit **the same**
`bridge-vlan` model in `/etc/config/network`, so they had to share one design language and had to
read and write configuration in exactly the same way.

All color values, font sizes, and spacing values in this document are the single source of truth; the `var css` in
`meshconf.js` and `switch-vlan.css` are its two mirrors (see "Why two mirrors instead of one shared file" at the end).

## 1. Problem diagnosis

### 1.1 Visual inconsistency (before the change)

| Dimension | switch-vlan | meshconf (before the change) |
| --- | --- | --- |
| Color source | LuCI theme variables (`--background-color-*` / `--text-color-*` / `--border-color-*` / `--primary-color-high`), following the theme | Hard-coded GitHub Primer palette (`--nm-*`), **completely ignoring the theme** |
| Dark mode | `:root[data-darkmode="true"]` overrides | Reads the brightness of `document.body`'s background color at runtime and concatenates strings |
| Font size | `em`, relative to the LuCI theme base font size | Fixed `font-size:13px` plus its own `font-family` |
| Border radius | 2px / 4px | 8 / 9 / 10 / 12px |
| Spacing | Loose `em` scale | Hard-coded px |
| Breakpoint | 720px | 900px / 760px |
| U / T semantics | Teal `#0d9488` / amber `#d97706` pill buttons | Plain-text `U` / `T` in `<select>`, with no color |

Conclusion: the two pages did not use the same colors, font sizes, or border radii, and each had its own dark-mode mechanism.
The most important point is "following the theme" -- meshconf's fixed palette made it look unlike the surrounding pages
on a router using a dark theme.

### 1.2 Configuration inconsistency (before the change, with evidence for each item)

| # | Symptom | Evidence | Consequence |
| --- | --- | --- | --- |
| 1 | meshconf **cannot read** port markers written by the official page | Upstream `tools/bridgevlan.js` writes untagged/PVID ports as **bare port names** (`lan3`) in `formatPortSpec()`, and writes tagged ports as `lan3:t`; this page's `vlan_ports_of()` only recognizes `*:u*` and `*:t*` | `lan3` (or `lan3:*`) configured on the official page is shown as "not joined" on this page; once this page is "applied", it **silently deletes** that port from bridge-vlan |
| 2 | `option local` was never written | netifd defaults a missing `local` to **true**; the official view has a Local checkbox (`parseLocal()`), while this page had no such concept | bridge-vlan generated by this page happened to align with the official page's display semantics only because of the default value; once someone clears Local on the official page, this page would still create a `br-lan.<ID>` interface, while netifd would not create that device at all |
| 3 | The DHCP server switch is **always unchecked** | `dhcp.checked = false` is hard-coded in `buildVlanRow()`; `getStatus()` also did not return that state | Reapplying any VLAN change even once (even just adding a subnet) made `apply_vlans()` write `dhcp.<iface>.ignore='1'` for unchecked subnets, **turning off an already running DHCP server** |
| 4 | This page allows "the same port to be U in two VLANs" | The official `bridgevlan.js` treats this as unsupported in `checkUnsupportedConfig()` and **refuses to render the entire page**; this page's `vlanErrors()` only checked ID range and duplicates | This page could write a configuration that the official page refuses to display |
| 5 | The port grid lists more ports than the official page | The backend `bridge_port_list()` returns all members of br-lan, and the frontend only filtered out `bat0` | Virtual interfaces such as `wlan0` / `phy0-ap0` / `mesh0` were offered U/T options as if they were switch ports; writing them into `bridge-vlan.ports` is meaningless |
| 6 | Port marker spelling differed from other writers in the tree | Before the change it wrote `"${port}:u*"`; the official view writes bare `lan3`; `config_generate` also writes board-level raw values | Two styles appeared in the same configuration |

`:root[data-darkmode="true"]`, overriding only semantic accent colors -- surfaces and text are already provided by theme variables.

> Why the glow can be only 1.6:1: it is **not** the basis for compliance. The focus state is a three-layer stack -- a 3px soft glow
> (soft transition, also looks good on mouse click), a 1px primary border, and an additional 2px primary outline when triggered by the keyboard.
> The latter two are 5.19:1 / 5.81:1; either layer alone already satisfies the 3:1 requirement in SC 2.4.11.
> Conversely, the **glow alone must not** be kept: that is why the previous version was wrong to use `--ds-info-tint` (alpha `.08`, only
> **1.12:1** after compositing) as the 3px focus ring. This change uses the dedicated `--ds-focus-ring` instead (`.32`,
> 1.61:1, 1.44 times the former value) and removes `:focus{outline:none}` -- it is in the same family as
> `.meshconf-page :focus-visible` but has higher specificity (`.nm-field input:focus` = 0,2,1 >
> `.meshconf-page :focus-visible` = 0,2,0), so it swallowed the global keyboard outline as well, causing an SC 2.4.7
> regression. Keyboard focus is now explicitly restored by `:focus-visible`.
> These two numbers (1.12 / 1.61) are calculated and asserted by `scripts/luci-ui-checks/ringcheck.js`.

## 3. Font scheme

One rule: **use only `em`; do not write px, and do not override `font-family`.**

The LuCI theme decides the base font size (bootstrap 13px, material 14px, and so on). Hard-coding 13px makes the whole page
one size smaller in a 16px theme; `rem` also falls back to 16px because themes usually do not set a font size on `html`.
Therefore the relative scale can only use `em` (switch-vlan already does this).

| token | Value | Purpose |
| --- | --- | --- |
| `--ds-fs-xs` | `.8em` | Table annotations, badges, legends |
| `--ds-fs-sm` | `.88em` | Auxiliary text, hints, table body, buttons |
| `--ds-fs-base` | `1em` | Body text, inputs, field labels |
| `--ds-fs-lg` | `1.1em` | Section titles, statistic values |
| `--ds-fs-xl` | `1.35em` | Main statistic values |
| `--ds-fs-2xl` | `1.6em` | Page title `h2` |

Monospace fonts are used only for device names, VLAN IDs, and configuration previews: `ui-monospace, SFMono-Regular, Consolas, monospace`.

**`em` compounds at each nesting level**: `.nm-table` is `.88em`, and `.nm-mono` inside it is multiplied by `.8em`, leaving only
`0.70em` (about 9px with a 13px base). Therefore elements that are "nested inside a table / key-value pair" are explicitly restored:

```css
.nm-table .nm-mono, .nm-table .nm-state, .nm-table .nm-tag, .nm-kv-item .nm-mono { font-size: .95em; }
```

## 4. Layout, spacing, and border radius

| token | Value | Notes |
| --- | --- | --- |
| `--ds-sp-1` ... `--ds-sp-5` | `.25em / .5em / .75em / 1em / 1.5em` | Four-level spacing scale, all in `em` |
| `--ds-r-sm` | `4px` | Inputs, small badges, segmented controls |
| `--ds-r-md` | `6px` | Cards, port tiles, row containers |
| `--ds-r-lg` | `8px` | Section cards, topology canvas |
| `--ds-r-pill` | `999px` | Status pills |

- **Grid**: always use `repeat(auto-fit, minmax(<min>, 1fr))`; do not write media queries.
  Form `.nm-form` minimum 190px, choices `.nm-choices` minimum 240px, AP cards 260px,
  info grid 148px, ports 11em (inherited from switch-vlan).
- **Only one breakpoint**: `720px`, the same as switch-vlan. Before the change, meshconf used two
  breakpoints, 900/760, causing the two pages to change shape at different window widths.
- **Touch targets**: each segmented-control button uses `min-width:26px; min-height:24px`, satisfying
  the 24x24 minimum target in WCAG 2.2 SC 2.5.8.

(off / untagged / tagged), the color semantics are the same, and the rule that one port may have only one untagged VLAN is also
the same**; only the control shape follows each page's workflow.

## 6. Accessibility checklist

- [x] Body-text contrast >= 4.5:1, non-text UI >= 3:1 (see §2.3 for data)
- [x] Visible focus: `.meshconf-page :focus-visible` and `#switch-vlan-view *:focus-visible`
      share a 2px primary-color outline; buttons inside tables use `outline-offset:-2px` to avoid clipping
      (WCAG 2.2 SC 2.4.7 / 2.4.11)
- [x] Inputs do not swallow the keyboard focus ring: the original `:focus{outline:none}` had higher specificity than the global
      `:focus-visible` rule and canceled the keyboard outline as well; it is now split into
      `:focus` (primary-color border + glow) and `:focus-visible` (restored 2px outline).
      The glow uses dedicated `--ds-focus-ring` (1.61:1 after compositing), and compliance is carried by the 5.19:1 border/outline
- [x] Measured focus-ring contrast appears in §2.3 "Layered focus-indicator measurements"; no case relies on only a 3px faint glow to satisfy 3:1
- [x] State is not conveyed by color alone: status pills include a dot + text; conflicted VLAN rows include a
      `title` describing the specific port in addition to the border (SC 1.4.1)
- [x] Segmented controls are real `<button>` elements, with `aria-pressed` and `role="group"` +
      `aria-label`, and are keyboard-operable
- [x] Touch targets >= 24x24 (SC 2.5.8)
- [x] Prefer semantics: `<button type="button">`, `<summary>`, and `<label>` wrapping controls;
      no `div` substitution just for styling
- [x] Dark mode no longer guesses at runtime: `data-darkmode` is an attribute declared by the theme itself
- [ ] **Not covered**: the topology SVG's `aria-label` only gives an overall description; node-level information is still provided in parallel as a text table
      (`.nm-table`). A fully equivalent text representation needs separate work if required

## 7. Configuration consistency fixes

### 7.1 Backend `root/usr/libexec/rpcd/luci.meshconf`

1. **Port marker parsing changed to the same syntax as upstream** (new `vlan_port_role()`):
   `port` / `port:u` / `port:u*` -> untagged; `port:t` / `port:t*` -> tagged;
   `port:ut` -> both; `port:*` -> PVID only, neither one; invalid -> `n`.
   **Verification**: this function and the real upstream `parsePortSpec()` source in `tools/bridgevlan.js` were
   extracted separately and compared case by case for 17 markers; all 17/17 matched.
2. **Writing changed to canonical spelling**: untagged ports are written as bare port names (removing `:u*`), matching the official view's
   `formatPortSpec()` and the spelling used by `config_generate`.
3. **Explicitly write `option local`**, and truly decide whether to create an interface from it:
   - `local=1`: create the `br-lan.<ID>` interface + DHCP + firewall zone members as before;
   - `local=0`: pure Layer 2 passthrough, **do not create an interface**, and delete any leftover interface of the same name (together with its dhcp section and
     zone members) -- otherwise it would hang off a device that netifd will not create;
   - VLAN 1 is always `local=1` (the management address is on `br-lan.1`), and the management VLAN synthesized in `vlan_sync_lan_device()` also gets `local=1`.
4. **Reject markers that cannot round-trip losslessly**: new `vlan_foreign_specs()` rejects apply when
   `port:ut` or `port:*` appears on br-lan and reports the exact marker; `getStatus()` adds a
   `vlan_foreign` field, so the frontend shows a banner early in the "Current status" section instead of waiting until Apply is clicked.
5. **Reject cross-VLAN untagged conflicts**: the new corresponding check in `vlanErrors()` plus a backend
   **pre-write validation** in `apply_vlans()` (the entire payload is validated before touching UCI, avoiding a half-modified but uncommitted configuration
   left in the rpcd session when validation fails and accidentally committed by the next call).
6. **Return real state**: `vlan_list()` adds `"local"` and `"dhcp"`; `dhcp` is inferred from
   `dhcp.<iface>.ignore` and `.dhcpv4`. The frontend initializes checkboxes from this state,
   eliminating the data-corruption path where reapplying turns off the DHCP server.
7. **Port list keeps only physical ports**: new `is_physical_lan_port()` excludes
   `bat0` / `mesh_*` / `wl*` / `wlan*` / `phy*` / `br-*` / `tun*` / `tap*` /
   `ppp*` / `wg*` / `gre*` / `sit*` / `6in4*`. netifd also places these interfaces into br-lan,
   but none of them can carry the tagged egress this page wants to write.

### 7.2 Frontend `htdocs/.../meshconf.js`

- Field names are aligned with the LuCI network page wording: `IPv4 address` / `IPv4 netmask` / `IPv4 gateway` /
  `DNS servers` / `Enable DHCPv4 server` / `Interface name (UCI name)` -- the same value uses the same name on both pages.
- Add a "Local termination (assign address)" checkbox; when unchecked, the address fields are hidden as a group
  (with no `br-lan.<ID>`, there is no address to configure), and explanatory text is shown. The VLAN 1 checkbox is checked and disabled.
- Port cells changed from `<select>` to a `- / U / T` segmented control; selecting U **automatically** removes that port from
  U in other rows (matching the official view's `applyUntaggedVlanToSelection()` behavior), with validation as a fallback for invalid configurations.
- Each row marks conflicts from `untaggedOwners()` (outline + `title`).
- Focus styles are split into two rules: `:focus` only gives the primary-color border + 3px `--ds-focus-ring` glow,
  while `:focus-visible` **additionally** restores a 2px primary-color outline. The reason is that the original
  `.nm-field input:focus{outline:none}` ((0,2,1)) had higher specificity than the global
  `.meshconf-page :focus-visible` ((0,2,0)) and canceled the keyboard outline as well -- the same pitfall
  existed in upstream switch-vlan too (see §7.3).

### 7.3 Upstream `view/network/switch-vlan.css` (feed patch)

`patches/feeds/luci/.../view/network/102-align-switch-vlan-design-tokens.patch`:

- U/T text colors -> `#0f766e` / `#92400e` (contrast 3.25->4.86, 2.75->7.09)
- Keyboard focus visibility rules (see below), port tile radius 4->6px, input radius 2->4px

**Why the focus rule must be written this way**: upstream has three `:focus { outline: none }` rules. One of them,
`#switch-vlan-view input[type="text"]:focus`, has specificity (1,2,1), while
`.svc-port-label` / `.svc-vlan-label` are `<input type="text">`, and
`.svc-vlan-id-input` is `<input type="number">`; **all are matched by it**. Therefore:

- Adding a "convenient" `#switch-vlan-view input:focus-visible` ((1,1,1)) **loses** to it,
  so the patch applies successfully but changes nothing -- keyboard users still cannot see focus;
- The correct approach is to **mirror the upstream selector** to tie specificity ((1,2,1)), then place the rule block at **the very end of the file**
  and win the tie by source order. Therefore this block must remain at EOF.

At the same time, keep `outline: none` on `:focus`: mouse clicks show only the primary-color border (the original upstream visual intent),
and the focus ring is restored only for `:focus-visible` (keyboard).

**Verification**: in a temporary git repository (root = feed root), the upstream original file was processed exactly as the build script does
(`git -C <feed root> apply` reading stdin); both `--check` and the application succeeded.
A tiny cascade evaluator also simulated "which element has keyboard/mouse focus, and which `outline` wins";
see item 8 in §10.

## 8. Evaluated but **not** changed

| Item | Conclusion |
| --- | --- |
| Add a feed patch for meshconf that "keeps only physical bridge members" | **Not needed**. The original assumption was that `bat0` would make `findActiveBridge()`'s all-port `switch`/`ethernet` check fail and block the whole switch-vlan page as "unsupported configuration". Checking `Device.getType()` in `luci-base/.../network.js` showed that it **has no** special case for batman-adv; `bat0` falls through to `else return 'ethernet'`, so this check passes. The existing `100-skip-wireless-bridge-members.patch` already handles the real failing class (VAPs with `getType()==='wifi'`). |
| Have meshconf write `option vlan_filtering '1'` | **Do not do this**. In `tools/network.js`, this option's default value is inferred from "whether a `bridge-vlan` section matching the `device` exists", and `bridgevlan.js`'s `isVlanFilteringEnabled()` also treats "bridge-vlan exists" as enabled. Writing it separately from meshconf would only create differences, without adding any behavior. |
| Unify all upstream style border radii to the scale | **Only port tiles and inputs were changed**. VLAN row radii are written on the first and last cells as `4px 0 0 4px`, requiring four coordinated edits; the benefit is small and the rebase cost after upstream drift is high, so this is left blank. |
| Build a complete graphical flow for "pure passthrough subnets" | The backend supports `local=0` and the frontend can express it, but validation currently blocks the combination "local termination off + this page still wants to create an interface" and prompts the user to manage it from the network page. Making an end-to-end usable passthrough editing flow also involves coordination with `vlan_sync_lan_device` and SSID binding, outside this change's scope. **Do not confuse this with §11 "bridge-level full passthrough"**: the latter means **the entire bridge uses no `bridge-vlan` segmentation at all**, and one-click switching back is implemented. The missing work here is per-subnet passthrough editing (`br-lan.<ID>` + `local=0`). |

## 9. Why two mirrors instead of one shared file

The two pages belong to two packages: `luci-mod-network` comes from a feed patch, while `luci-app-mesh-conf` is this repository's
package, and **either may exist alone** (mesh-conf can be uninstalled). Making the upstream style `require` a file provided by
this package would hard-bind the installation relationship between the two packages; the reverse dependency would have the same problem.
Therefore the choice is: **values are defined uniquely in this document, and each side inlines the same token block**, with both code locations
pointing back to this file. The cost is that color changes must be made in two places; the benefit is that either page works independently.

## 11. Wizard default policy (phase 2)

This section records the wizard's "works out of the box" defaults. The principle is: **the default configuration should not require the operator to understand the `bridge-vlan`
model, and should not require item-by-item settings to form a network**; explicit switching is used only when fine-grained control is needed.

### 11.1 Layer 2 default: "full passthrough"

When VLAN segmentation is not enabled, **no settings are required**: on a node without `bridge-vlan` sections, `bat0` as a
**normal member** of `br-lan` carries all traffic by itself, with one subnet across the entire network.

- Backend adds `apply_flat_bridge()`: delete all `bridge-vlan` sections on `br-lan`, delete
  leftover `br-lan.<ID>` interfaces (skipping `lan`), and write back the collected physical ports.
  This is **the only exit from filtered mode back to flat mode**, triggered by `callApplyVlans(payload, 'flat')`
  (custom segmentation uses `callApplyVlans(payload, 'custom')`; the two paths are explicitly separated and do not depend on a backend default).
- Frontend `renderVlanSection()` offers flat / custom as two choice cards, with **flat as the default**;
  custom is defaulted only when the bridge is truly filtered and VLANs exist.
- ⚠️ **Ordering pitfall**: `network.lan.device` must be set to `br-lan` **before** calling `ensure_lan_bridge()`.
  Otherwise `ensure_lan_bridge()` treats the old value of `network.lan.device`
  (for example `br-lan.1`) as a **literal port** and adds it back to the bridge members.
- In filtered mode, `trunk` (whether `bat0` passes each VLAN across nodes) is **enabled by default** --
  if the flag is missing, treat it as `bat0:t`; only explicit `0/false/no/off/disabled` excludes it.
  This prevents "creating VLANs one by one" from producing a machine whose backhaul is disconnected.

### 11.2 Backhaul: wired by default, wireless only on 5G/6G

- **Wired backhaul** is selected by default (`br-lan` as a whole bridge acts as `batadv_hardif`, and bat0 bridge loops are avoided).
- Wireless backhaul **allows only 5G/6G**: backend `apply_mesh()` reads `wireless.<radio>.band`,
  returns `success:false` with a reason directly for non-`''/5g/6g`; frontend `backhaulCandidates`
  keeps only `band === '5g' || '6g'` (**no longer falls back to all radios**), prefers 6G when available,
  and disables radio selection with a reason when there is no candidate or `wpad-mesh` is missing.
- The reference implementation (`orangeyoo/XR1710G-OpenWrt-iStoreOS-Community`'s `MESH-GUIDE-ZH.md`)
  is **6G-only**; its channel/EHT160 defaults were **not copied** -- this wizard explicitly requires both 5G and 6G to be allowed.

### 11.3 Wireless coverage: one switch, no more SSID editing

`generate_child_config()` **copies the entire** `/etc/config/wireless`, so SSID / encryption /
key **do not need to be rewritten by this page at all**. Therefore:

- Remove the per-SSID editor and replace it with a **read-only** coverage summary `coverageRows()` (one row per radio,
  showing the SSID name and channel information), paired with a single `apSyncInput` checkbox.
- The checkbox's **semantics reverse with the role**: for primary/peer devices it means "push each radio's wireless configuration..." (checked by default),
  while for child devices it means "accept each radio's wireless configuration from the primary..." (checked by default). Clearing it preserves the local current AP settings.
- `getStatus()` adds `ap_sync_set` to distinguish **"the user explicitly cleared the checkbox"** from **"never configured"** --
  only the latter follows the default checked state, preventing intentionally cleared nodes from being pulled back into push mode.
- Channel planning is changed to a standalone "Apply channel plan only (do not change Mesh)" button, no longer coupled to Mesh Apply.
- `ap_configs` may be an empty `[]` (the backend allows an empty per-radio payload), and the frontend no longer collects
  per-SSID content.

### 11.4 Remove configuration backup and rollback

`backup_configs` / `backup_rotate` / `list_backups` / `restore_backup`, their three call sites,
the `backups` field in `getStatus()`, the ACL `listBackups` / `restoreBackup`, and the entire frontend
`renderRollbackSection` UI were removed in **five places**. Please back up the device yourself before changing configuration
(`/etc/config/`).
